TODOPOP 最新设计评估与下一步方案

日期：2026-10-23。当前代码基线：76a6f0a。本文是评估和建议，不代表本轮已实现这些改动，也不自动覆盖现有产品规则文档。

建议采用这次讨论的新方向：点击进入任务，✓ 才完成；无链接任务进入本地 billboard；控制条固定；分组配色列为核心功能。实施上先打通交互和退出路径，再移植挤压效果，最后完成整组移动。

1. 评估依据与边界

已打开并检查 设计师的 Claude mockup 和 Granola 会议共享页。会议页可读内容与本次贴出的总结一致；没有拿到额外逐字稿。

实际操作了字标的三个入口、任务表单、Tint、Popped、新建分组和分组换色。看到了一个 Canvas 气泡场景，以及对应的界面控件。未验证 Canvas 气泡拖动、碰撞手感和 billboard，不把它们当作已验收的功能；没有获取原型源代码，也无法判断其内部物理算法或具体框架。创建的 New group 仅用于原型交互检查，不是生产桌面任务。

同时复核现有 Electron/React 实现的任务点击、窗口管理、分组、配色、增长和归档代码。本轮只新增方案文档，不更改运行中的应用。

2. 对设计方向的判断

值得保留的部分

  • 进入与完成分离。 点击任务是开始处理它，✓ 表达完成。两种行为分开后，有链接和无链接任务都能遵循一致逻辑。
  • 本地 billboard 有实际用途。 “Feed your pet”这类现实任务需要可见提醒，不需要伪造网页或先配对浏览器。它补上了原先产品只擅长网页任务的缺口。
  • 固定的字标控制条。 相比一个可以漂移的大面板，更容易反复找到，也能为气泡布局提供稳定避让区。
  • 气泡形态、字标与收据统一品牌语言。 这套视觉比普通待办列表有辨识度，值得保留，不需要再换一套设计。
  • 长收据合理。 它表达完成的积累，滚动可以成为有意的体验；不必为了首屏整齐而砍短历史。
  • 色彩属于核心交互。 分组颜色帮助识别和组织，色相、饱和度与实时预览应进入核心范围，不能最后再当装饰补上。

需要修正的风险

“一直存在”不等于“一直移动、一直变大”。 任务可以持续留在桌面，直到完成；但气泡不应持续漂过鼠标、挡住工作内容，或越长越难点。移除 Pause 是减少一个用户决策，不应取消系统对增长、遮挡和失控的约束。

极简字标需要入口提示。 三个 O 是很好的品牌设计，但新用户很难猜出每个 O 的功能。悬停显示图标和短标签，键盘聚焦时同样显示；首次使用只提示一次。不能依靠演示者解释才知道怎么操作。

普通任务不一定需要全屏。 Billboard 应让任务清楚可见，同时允许用户去现实中完成它。建议第一版做大字号的本地专注窗口，有明确返回与完成按钮，不强制占用 macOS 原生全屏/新 Space，也不锁住其他应用。

完成仍需可恢复。 新版把完成放进指定区域后，依然可能误点。现有 Undo 仅服务删除；建议新增“撤销完成”，恢复同一任务和等待时长。它与 Re-bubble 创建新一轮必须分开。

点击气泡上的 ✓ Pop 并记录完成 不同时触发打开链接或 billboard

✓ 是“完成任务”的唯一语义入口，但可以在气泡、billboard、列表中有等价按钮。视觉按钮可小巧，实际命中区建议保持 32–40px，初版沿用当前固定 32px；不能随着气泡缩小或变形。WCAG 的指针目标最低要求为 24×24 CSS px，存在规定的例外；这里建议的尺寸是更宽松的产品目标。W3C 目标尺寸说明

Pop 热区应在悬停/聚焦时清楚显示，并提供短提示。小气泡空间不足时把操作停靠在气泡外侧安全区，不把全部按钮硬塞进小圆。拖拽超过约 6px 才识别为移动，这只是待实测的初始参数。

5. Billboard 的最小完整版本

窗口只包含任务名、可选组标识、“返回”和“完成”。先不增加步骤、倒计时、计时条、白噪音或 URL blocking。

  • 大字居中；短标题建议 48–72px 起步，长标题自动换行并设置最小可读字号。中文使用可覆盖中文的 Sans 回退字体。
  • 同时只保留一个本地专注任务。其他气泡暂时隐藏，固定控制条/退出入口保持可找，退出后恢复位置。
  • 切换到其他应用不会自动完成，也不自动结束本地会话；现实任务不能依赖浏览器前后台。
  • 进入 billboard 后该任务停止增长，建议其他气泡也暂停增长；这是专注态内部规则，不重新放回 Pause 按钮。
  • 关闭窗口等同返回；程序重启默认回桌面，不强制恢复一个覆盖屏幕的 billboard。
  • 保留历史专注时长时，在退出、完成、删除或应用退出时正确结束会话。期间睡眠不应被当成有效专注时长。

现有 NORMAL / FOCUS 只有自动浏览器语义，不足以承载新版。建议拆出本地会话状态 idle / billboard(taskId)，浏览器匹配单独保留。Demo 期间，本地会话优先，Chrome 的失焦、断开或不匹配 URL 不能把 billboard 关掉。操作 TODOPOP 自己也不结束本地会话。

有链接任务在正式版仍可直接打开 URL。如以后也需要本地专注，在编辑层提供显式“专注此任务”，不要让同一次普通点击偷偷触发两套不同会话。

6. 固定控制条、三面板、字体与收据

建议控制条默认固定在主屏上边缘中部，避开菜单栏。它不随气泡碰撞漂移；设置里可切换停靠边，窗口边界变化时重新夹紧。最终位置由设计师确认，先不要开放自由拖拽。

“第三个泡泡”有歧义：可能是字标第三个 O，也可能指另一个设计里的气泡入口。会议还没有在共享页列出“三个面板”的名称。本方案暂以“新增任务 / 已完成收据 / 分组与配色”作为排期假设，不能据此直接编码成已确认设计。

如果目标确实是第三个 O 一次展开三块：控制条固定，三块组成同一个工作区；只维持一个组编辑浮层。宽屏可并排，小屏按可用工作区叠放或折成标签页。关闭工作区用 Esc，关闭子浮层先退一层。展开区域要加入布局避让，不把底下任务盖住。

Unbounded 已符合圆润、玩乐的品牌方向，建议继续用于字标、标题与短任务名。表单、辅助说明与长文本要单独检查字宽、行高和中文回退，优先增大阅读字号，避免通过整体缩放把控件压成很小的字。调色后普通正文对背景建议至少 4.5:1，大号文字至少 3:1；任意组色可以保留在色点/浅填充，文字自动选安全深浅色。W3C 对比度说明

Popped 保留长收据造型、日期分隔和滚动条。外部面板高度受工作区约束，内部收据可以很长；不要让原生窗口一路长出屏幕。先保障 100 条记录流畅，再考虑更多记录的按批加载。任务创建后跨天仍存在；按日/周/月看已完成历史与“不按日重置任务”并不冲突。

日期徽标建议悬停显示完整日期，避免“23”被误解为剩余数量、优先级或截止日。TODAY 则需要辅助说明是紧急程度，而非当天自动到期。

7. 分组：先做好颜色，再加入整组移动

现有数据已经支持稳定组 ID、自定义 HEX、组名、增删和侧边位置，应该沿用。

建议组编辑面板提供：名字、位置、色相、饱和度、预设色、HEX、删除。亮度可由设计 token 控制以保证可读性；若开放亮度，也应保留对比度检查。全局 Tint 影响品牌界面，组色影响成员气泡，两者不能无提示地互相覆盖。改色即时预览，拖滑杆时节流保存，放手后提交最终值。

选中组时，成员显示清楚的描边/标签，其他组降低到约 35%–50% 可见度，数值以真实壁纸测试为准；不能只靠颜色区分。提供组边界或专用移动手柄。普通气泡点击仍进入任务，整组移动只由该手柄触发，避免同一主体点击因隐藏模式而改变意义。

移动时临时暂停相关布局自动重排；松手后保存整组锚点和成员偏移，再让碰撞缓和收敛。现有 side 只能表达贴边，不能表达任意二维组位置，因此需要补组布局数据。移除组只解除归组，成员任务留在桌面；如果要连任务一起删，必须另设明确操作。

8. Squish 的工程方案

框架不同不等于算法不能复用。应从另一版本提取气泡的受力、边界形变、拖拽阻尼和参数，再接入当前 React/Electron；没有源码前，不承诺精确复刻，也不按 zip 能否直接运行判断可行性。

当前版本是每颗气泡一个透明原生窗口，内部 SVG + Motion，布局采用圆形排斥。Mockup 的场景包含 Canvas。两者主要差异是绘制和窗口/事件模型，不一定需要重写任务、历史、存储或 IPC。

建议先做一个小型移植验证，比较两种路径：

路径 收益 代价与门槛
延用独立气泡窗口，加入局部边缘形变和拖拽回弹 保留已测过的点击穿透、生命周期、编辑层和 Focus 窗口裁切、变形留白、跨窗口接触与同步要验证；更适合先做有限形变
每个显示器一个透明场景窗口，统一 Canvas/SVG 绘制 群体碰撞、软体挤压和组移动更自然 必须重新解决空白区点击穿透、鼠标捕获、层级、多屏、Dock/Spaces；不能仅因网页视觉好看就直接采用

优先验证第一条路径；若独立窗口无法达到目标手感，再用第二条路径替换气泡显示层。 任务数据与交互状态应独立于绘制方式，避免之后重复重写业务逻辑。

不论选哪条路径，都遵守：

  1. 空闲只有小幅形变/呼吸，气泡中心不持续游走；鼠标接近时目标稳定。
  2. 拖拽、碰撞、成长才触发明显挤压，松手后逐渐收敛，不持续震荡。
  3. 文字和 ✓ 不跟着软体边缘被挤成不可读形状。
  4. 视觉轮廓与命中区域要一致，不能可见处点不到、透明处挡住其他应用。
  5. 固定控制条和展开面板是障碍区，气泡绕开它们。
  6. 限制单泡可见直径，建议从可用屏幕短边的约 70% 开始实测；接近上限改用有限形变/拥挤表达。任务继续存在，不再无限长出屏幕。
  7. 达到容量时停止增加几何尺寸，但仍能完成、编辑、退出和在列表中定位任务。不要用“屏幕满了”让所有操作失效。
  8. 减少动态效果设置使用稳定位置和轻量过渡；记录真实设备性能后再设数量上限。

透明窗口的鼠标事件忽略/转发由 Electron 提供，但仍需真实桌面测试；网页预览通过不代表桌面穿透正确。Electron BrowserWindow 文档

10. 推荐实施顺序与交付标准

阶段次序基于依赖和可验收性，不是已承诺工期；拿到另一版源码并完成技术验证后再估时。

阶段 工作 阶段完成标准
0 · 冻结交互稿 确认三面板、billboard 出口、分组高亮/移动、色控、增长速率；列出截图状态 无链接点击不再有“进入/完成”两套说法；设计和测试采用同一规则表
1 · 完成交互闭环 新点击路由、本地 billboard、固定 ✓、Esc/返回、撤销完成；与浏览器 Focus 分离 完全离线、未装扩展仍能从新建到专注再完成；拖拽不误触
2 · 固定 UI 与必需色控 固定字标、三面板适配、组色 H/S、移除 Pause、旧状态迁移、日期/收据 小屏不出界，任意组色文字仍清楚，重启后设置/历史不丢

色彩控件安排在 Squish 之前，是因为它已经被明确列为 must-have；不能用动效占满时间后再把它推迟。整组移动依赖稳定布局，放在物理/布局方案选定后。展示稿在阶段 5 收敛，营销网站、手机、后端和同步保持延期。

11. 测试与人工复核方案

12. 开始开发前剩下的四个确认点

  1. “第三个泡泡”的具体入口，以及同时展开的三块内容是什么？现有原型是三个 O 各开一块。
  2. Billboard 的初始视觉范围：建议可退出的大字窗口；若要覆盖整块屏幕，需提供对应设计状态。
  3. 正式增长速率采用会议前方案，还是 mockup 的较慢速度？先统一一份表，Demo 倍速另算。
  4. 能否取得另一版本的相关源代码/导出，或至少给出拖拽、接触、成长三个状态的参考录屏？当前链接足以评估外观，不能据此承诺准确移植物理参数。

这些确认不妨碍先整理状态和测试，但会影响对应界面及 Squish 的最终实现。没有确认时，三面板排列与物理框架选择都应保持可替换。

13. 演示与上线形式

Hackathon 演示建议围绕一条主线：创建任务 → 气泡持续提醒并挤压 → 点击无链接任务进入 billboard → 返回 → 用 ✓ Pop → 收据出现完成记录 → 改组色并整组移动。网页链接与 Chrome 配对放在次要支线，避免让安装扩展成为理解产品的前提。

真实主流程稳定后，再安排可复位的演示样例。Demo 增长使用独立预览数据，避免演示加速污染用户任务；不要用无法复现的假前台切换冒充自动 Focus。扩展发布是独立交付项，有审核和分发前置条件，不能保证与演示当天同步完成；需准备清楚标注的开发者加载或录屏备选。

首发维持本地桌面应用，不需要账号和后端。先做 macOS 安装包，补开发者签名、公证、更新/版本区分与干净机器安装验收；按你们的决定，首发去除扩展依赖。手机遥控、云同步、URL blocking 与营销网站继续后置。

依据：用户讨论记录、共享原型、当前本地代码。网页观察不等于桌面性能或交互验收。
